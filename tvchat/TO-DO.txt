tvchat does IRC (with IRCv3) and talk(1). What is left is below, in the order
it is likely to be done. Defects live in BUGS.md, not here.

Next
1 Delta Chat, what is left (tvchat/DESIGN.md "Delta Chat adapter"; tried live on
  cpbee with two mailboxes, and on cmlaptop and cmdesktop):
  - Attachments (shown as `[attachment: NAME]`), reactions, multi-device setup,
    a chat renamed on another device (the title is refreshed but no event tells the
    UI), a group's picture and description, broadcast channels.
  - Groups: the member picker could list the people you already hold keys for
    (Add member asks for an address today); Leave deletes the chat but does not
    block the sender, so a new message may come back as a request.
  - Invitations by mail need the account's mail servers (imap_server /
    smtp_server, or the address's domain): ask the core for its transport when
    they are not in tvchat.conf.
  - An invitation could also arrive from tvmail (see 12).
  - Tests: `TestDeltaChat`, `TestDeltaInvitations` (a stub core and a fake mail
    server) and `TestDeltaChatRealCore` (skipped without a core that runs;
    `$TVCHAT_TEST_DC_RPC`); `delta_invite_join_and_send` in e2e_regress.

Open questions
- Should IRC logs persist to disk between sessions? Not for now: the log is
  the backend's in-memory ring (2,000 lines per conversation). Worth asking
  again if an always-on backend ever happens - that would be an IRC bouncer.
- Self-hosting Ergo on cpbee is done; how to keep it reachable if cpbee moves
  to a phone-tethered connection is not.

Wish list (not planned)
- A web version (an installable PWA that looks like the terminal app). The
  backend's protocol stays free of anything terminal-specific so a browser
  front end can reuse it.
  * Browsers cannot open raw sockets, so it needs a server-side WebSocket
    gateway relaying the same verbs and sequenced events to tvchat-backend.
  * Option A: the real app in a browser - xterm.js plus a pty over WebSocket
    (ttyd-style). Identical look, almost no new code, but a server-side
    session and account per visitor: a hosting and security project.
  * Option B: a Turbo Vision look-alike - a CSS character grid with the cyan
    desktop, menus and shadowed dialogs, talking to the gateway. More work,
    installable as a PWA.
  * IRC-only shortcut: a self-hosted Ergo accepts WebSocket clients directly;
    Delta Chat still needs the gateway.
  * Hosting: the static front end on GitHub Pages or cp1; the gateway (with
    the backends behind it) on cpbee or a small VPS - not cp1 (below).
  * The server needs the backends running permanently (one per logged-in user,
    holding their connections and credentials), a small WebSocket gateway
    (login, spawn, relay), a reverse proxy (nginx or Caddy: TLS via Let's
    Encrypt, WebSocket upgrade, rate limiting) and service units. On cpbee
    that also means an inbound 443 in the nftables input chain (policy drop
    today), and a tunnel (Cloudflare Tunnel, Tailscale Funnel) or a VPS relay
    if cpbee loses its public address. It is a public login page in front of
    mail and chat credentials: auth, TLS only, lockout. Server-side setup
    would be a new tool in chrispollitt/POSIX beside mail-setup.
- "Crazy talk": a gateway to OpenVMS PHONE, e.g. on the SIMH VAX (cpvax).
  PHONE speaks DECnet task-to-task (object 29), so it needs DECnet on both
  sides.

Why not cp1 (u-l.ca, the cPanel webhost; checked Oct 20, 2026)
- It can serve a static front end but cannot host the gateway or the
  backends: CloudLinux shared account; outbound IRC (irc.libera.chat 6697 /
  6667) refused over IPv4 and unreachable over IPv6, outbound 443 to Libera
  times out, only outbound HTTPS works; apps run under Passenger and are
  stopped when idle, with per-account LVE limits, so a permanently connected
  backend fights the idle shutdown, and credentials would sit on a shared
  server.

Decided: not doing
- No WhatsApp (unofficial clients risk banning the real mobile number), no
  Teams (the Graph chat APIs reject personal Microsoft accounts), no
  Messenger (no personal-inbox API). No file transfer over IRC (DCC), voice or
  video, no Matrix or XMPP backend, no threading or reactions UI.
