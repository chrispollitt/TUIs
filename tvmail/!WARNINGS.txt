** WARNING 1 **

Running tvmail over SSH from inside Windows Terminal does not work
correctly, whether you use Cygwin's ssh or Windows' native OpenSSH
client. Windows Terminal's ConPTY layer (and, for Cygwin, its own
pseudo-console bridge) sits between tvmail and the real terminal and
mangles the live terminal-capability negotiation tvmail depends on.
Depending on settings, you get either garbage escape sequences
bleeding onto the screen, or keystrokes and mouse clicks silently
dropped.

Workarounds, in order of preference:

  1. Run ssh from mintty instead of Windows Terminal.
  2. Run ssh from inside WSL instead of from Windows directly.

I added this Windows Terminal profile as my solution (option 2):

wsl.exe -d Ubuntu-20.04 ssh cmpi

(For the curious -- including the test that pinned this down -- see
the accompanying TERMINAL-HISTORY.md, particularly section 7 at the
end.)

If you'd like to help make this someone else's problem to fix: this
is a known, unresolved gap in ConPTY (microsoft/terminal on GitHub)
and in Cygwin's pseudo-console handling (the cygwin-patches mailing
list -- Cygwin has no GitHub tracker). TERMINAL-HISTORY.md section 7
is a ready-made bug report with a reproducible test case attached.
Old geezers who remember when terminals just worked are encouraged
to make some noise. ;)


** WARNING 2 **

IMAP servers disagree on folder-namespace layout, and mail(1)'s
"+name" plus-notation cannot bridge the difference.

cmpi's Dovecot puts folders at the namespace root (Sent, Junk,
Trash -- no prefix, "/" hierarchy delimiter). mail.u-l.ca
(cPanel/Dovecot) requires an "INBOX." prefix on everything except
INBOX itself, with a "." delimiter (Sent -> INBOX.Sent). A folder
name that's correct on one server is rejected by the other with
"Client tried to access nonexistent namespace."

tvmail-backend works around this automatically -- it discovers each
server's real folder name via RFC 6154 SPECIAL-USE attributes on a
plain LIST, rather than guessing the namespace layout (see
_imap_folder()/_imap_specialuse_map() in backend/tvmail-backend).

GNU Mailutils' mail(1) has no equivalent fix available. Its "+name"
expansion always inserts a literal "/" between the folder variable
and the name (manual: "the '+' sign is replaced by dir, followed by
a directory separator ('/')") -- there's no config that makes
"mail -f +Sent" resolve to "INBOX.Sent". You have to type the full
name yourself:

  mail --headers -f +INBOX.Sent          (mail.u-l.ca)
  mail --headers -f +Sent                (cmpi)

or wrap it in a shell function, e.g.:

  mailf() { mail --headers -f "+INBOX.$1"; }


** WARNING 3 **

Don't run tvmail in local mode on a host that's also running Dovecot
(or any other IMAP server) over the same mailstore -- even though
mode defaults to local whenever it's left unset (including when
tvmail.conf doesn't exist at all), which is exactly the case on an
unconfigured master.

Dovecot and tvmail-backend's local mbox code (Python's stdlib
"mailbox" module) are two independent programs that can both open,
lock, and rewrite the same /var/mail/$USER file, and their locking
conventions don't line up reliably. Hit this in practice on cmpi:
/var/mail there is root:mail 2775, chris isn't in group mail, so
local-mode delete failed outright with a permission error the moment
tvmail tried to rewrite the mbox out from under Dovecot's nose.

The fix, now the default setup for this project: even on the master,
point tvmail.conf at Dovecot over localhost ([imap] host = localhost
port = 993 verify = false) instead of local mode, so there's exactly
one program (Dovecot) ever touching the mbox files, and every other
box -- master included -- talks to it the same way, over IMAP. See
README.md's "Plumbing" section.


** WARNING 4 **

Pointing tvmail straight at a WAN/Internet IMAP host (e.g. [imap]
host = mail.u-l.ca) works fine -- nothing about the protocol requires
a local middleman -- but every folder switch, list and show is a
synchronous round trip the UI blocks on (see trace.sh), and each of
those round trips now costs real Internet latency instead of LAN
latency. Profiling a session against a WAN host with trace.sh showed
the backend spending the overwhelming majority of its time simply
waiting on the SSL socket read for the server's reply -- tens of
milliseconds per operation on a good connection, much worse on a bad
one -- and there's no way to hide that inside tvmail's single-
threaded, blocking design without a much bigger architecture change
(see the "busy" status-line indicator added instead, which just makes
the wait visible rather than eliminating it).

The fix is the same "Plumbing" setup as Warning 3, and it solves both
problems with one piece of infrastructure: run a local LAN Dovecot as
the master, have pop-pull (configure/configure-mail-pull.sh --timer N)
fetch mail down from the WAN host on a timer, and point every client's
tvmail.conf at that LAN Dovecot instead of the WAN host directly. Every
IMAP round trip then happens at LAN speed (single-digit milliseconds)
regardless of how slow or far away the real mail host is -- the WAN
latency still exists, it just happens once per pop-pull cycle in the
background instead of once per click in the UI. See README.md's
"Plumbing" section.
